# PR «Было → Стало»

Ревьюер должен понять изменение, не забирая ветку к себе. Поэтому каждый PR и каждый отчёт о
выполненной задаче содержит визуальное сравнение до и после. Текстовое «добавил кнопку экспорта»
заставляет верить на слово; пара скриншотов со стрелкой это доказывает и сразу показывает, где искать.

Это обязательная часть сдачи задачи, а не украшение. Если сравнение честно получить невозможно,
так и напиши в PR и объясни почему. Никогда не подделывай «Было»: не правь DOM, не рисуй макет,
не выдавай текущее состояние за старое. Поддельное «до» хуже отсутствующего.

## Что прикладывать

| Тип изменения | Скриншоты До/После | Стрелки | GIF До/После | Диаграмма зависимостей |
|---|---|---|---|---|
| Видимый UI (вёрстка, новые элементы, тексты) | да | если изменение мелкое на большом экране | если меняется взаимодействие | нет |
| Поведение/сценарий (формы, фильтры, drag, загрузка, анимация) | да | да, на ключевом шаге | **да** | нет |
| Бэкенд/API/CLI без своего UI | да: экран, где видно эффект, или вывод терминала/ответ API через `--text` | да, на изменённой строке | если это многошаговый сценарий | если менялась структура модулей |
| Техническая задача / рефакторинг | да: затронутые экраны как доказательство «визуально без изменений» | нет | нет | **да** |
| Смешанное | всё применимое из строк выше | | | |

Стрелка нужна, когда изменение не бросается в глаза: маленький элемент на большом экране, изменённое
число, новый пункт меню. Если весь экран новый, стрелка не нужна. Больше 3 меток на кадр не ставь,
иначе внимание размывается.

## Порядок работы

Скрипты лежат в `scripts/` рядом с этим файлом (дальше `$SKILL`). Им нужны Node 18+, Playwright
и `ffmpeg` для GIF. Playwright ищется в проекте, в основном checkout (для git worktree), в `NODE_PATH`,
в кэше скилла `~/.cache/pr-before-after` и в глобальном npm. Если его нигде нет, поставь один раз в
кэш: `npm i --prefix ~/.cache/pr-before-after playwright`. Не занимай Playwright у соседних проектов
через `NODE_PATH`. Если версия Chromium для этого Playwright не скачана, скрипты сами запустят
установленный Google Chrome. Всё запускай из корня проекта. Опции каждого скрипта описаны в его шапке.

«Было / Стало» в этом файле — рабочие названия. В самом PR заголовки, подписи к стрелкам, alt-текст и
описание пишутся на языке, выбранном на шаге 0.

### 0. Спроси, на каком языке оформлять PR

Язык выбирай до первого скриншота, потому что подписи к стрелкам впечатываются в картинки, и
переснимать их потом дорого. Проекты бывают русскоязычные, англоязычные, с иностранными ревьюерами,
поэтому язык разговора с пользователем не определяет язык PR.

1. Если язык PR уже закреплён в `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`, в шаблоне
   `.github/pull_request_template.md` или в памяти агента по проекту (файлы memory, которые
   подгружаются в сессию: например «PR bodies: English»), используй его и не спрашивай. Если
   источники расходятся, свежая запись в памяти важнее старого правила в репозитории. В отчёте
   напиши, откуда взят язык.
2. Иначе посмотри, на каком языке написаны последние смерженные PR
   (`gh pr list --state merged --limit 5 --json title,body`), и **явно спроси пользователя**. Если есть
   инструмент для вопросов с вариантами, используй его. Первым вариантом поставь язык прошлых PR с
   пометкой «рекомендую», дальше русский и английский, свой вариант пусть вводит сам.
3. После ответа запомни выбор, чтобы в следующий раз не спрашивать: запиши его в память агента по
   проекту, если она есть. Предложи также строку в `AGENTS.md` («PR оформляем на <языке>»), чтобы правило
   видели и другие агенты. Записывай в репозиторий только с согласия: это изменение в коде.
4. Если спросить нельзя (неинтерактивный запуск, CI, фоновый агент), возьми язык прошлых PR, а если их
   нет, язык README. В финальном отчёте напиши, какой язык выбран и почему.

### 1. Составь список сцен

По диффу (`git diff --stat <base>...HEAD`) определи, где изменение видно пользователю: маршрут, нужное
состояние (открытый диалог, выбранный фильтр, данные), ширина экрана, тема. Одна сцена — одна пара
кадров. Если затронуты мобильная вёрстка или тёмная тема, добавь отдельные пары под них.

Для каждой сцены выпиши одной строкой, какое требование задачи она подтверждает: пункт из тикета,
макет Figma, текст бага. Эта строка пойдёт под сцену в PR. Без неё ревьюер видит, *что* поменялось,
но не понимает *зачем*, и переспрашивает («почему иконка поменялась? это правильно?»).

Данные бери из сидов, фикстур или демо-скриптов проекта. Реальные данные клиентов, токены и личные
email в скриншоты не попадают.

### 2. Сними «Было» с базовой ветки

Подними базовую версию рядом, не трогая рабочую ветку:

```bash
git fetch <remote> <target> && git worktree add ../<repo>-pr-before <remote>/<target>   # или merge-base PR
cd ../<repo>-pr-before && <установка зависимостей> && <запуск приложения на другом порту>
```

`<remote>` — тот remote, где откроется PR. У проектов бывает несколько remote (зеркало на GitHub и
основной GitLab), и зеркало может отставать на десятки коммитов или быть заархивировано. Перед
работой сравни `git rev-list --count <зеркало>/<target>..<remote>/<target>` и бери базу оттуда,
куда пойдёт PR. Ветку задачи создавай от той же базы.

Снимай «Было» **до** того, как применишь миграции новой ветки к общей базе. Иначе старый код может не
запуститься или показать не то. Как запустить проект, авторизоваться и что делать, если база
несовместима, описано в `references/before-state.md`. Прочитай этот файл, если запуск не очевиден.

### 3. Сними «После» с теми же параметрами

Тот же маршрут, viewport, тема, данные и положение прокрутки. Тогда пара отличается только самим
изменением, и глаз сразу его находит.

```bash
node $SKILL/scripts/shoot.mjs --url http://localhost:5174/reports --out docs/pr/<slug>/01-reports-before.png
node $SKILL/scripts/shoot.mjs --url http://localhost:5173/reports --out docs/pr/<slug>/01-reports-after.png \
  --mark "[data-testid=export] => Новая кнопка экспорта"
```

- `--mark "селектор => подпись"` рисует красную рамку и стрелку от подписи. Подходит любой селектор
  Playwright: CSS, `text=…`, `role=button[name="…"]`, `:has-text("…")`. Рамка охватывает сам текст
  элемента, а не всю ширину блока. `--mark "селектор :: подстрока => подпись"` обводит только эту
  часть текста: `".post .label :: 3 мин чтения => Новое"`. Плашку скрипт ставит туда, где она
  меньше всего закрывает текст и где стрелка не пересекает строки, внутри области `--clip`. На «До»
  отметь место, где элемента не было или где было старое поведение. На «После» отметь новое.
- `--clip <селектор>` обрезает кадр по тому, что элемент реально показывает: текст и дочерние
  блоки, без пустого `min-height`. Края сдвигаются так, чтобы не резать строки на полуслове.
  Снимай крупный план изменения, а не весь экран. Если список длинный, ограничь высоту через
  `--viewport 1440x760`. Липкую шапку, которая наезжает сверху, убирай через `--hide header`.
- Подготовка кадра флагами, без отдельного файла:
  - `--click <сел>` (можно несколько, выполняются по порядку): открыть меню или диалог;
  - `--scroll-to <сел>` / `--scroll-y 600`: докрутить до секции;
  - `--hide <сел>` (можно несколько): убрать cookie-баннер, бейдж Next.js, виджет чата;
  - `--css "<правила>"`: поставить карусель на паузу и т. п.;
  - `--local-storage theme=dark`: тема, пройденный онбординг, язык до загрузки приложения;
  - `--delay "**/api/tasks*=3000"`: придержать запрос и поймать skeleton или загрузку.
- `--setup steps.mjs` нужен только для того, что флагами не сделать (логин через форму, drag).
- Если селектор не найден, скрипт через 8 секунд (`--timeout`) падает с одной строкой ошибки и
  списком похожих элементов на странице. Бери селектор из этого списка, а не угадывай заново.
  Вывод не обрезай через `| tail -1`.
- `--image raw.png --box "x,y,w,h => подпись"` ставит метки на готовый скриншот, например из
  симулятора или нативного приложения.
- `--text out.txt --title '$ команда'` превращает вывод терминала или ответ API в картинку для
  изменений без UI.

### 3а. Собери пару в одну карточку

Не ставь широкие кадры рядом в Markdown-таблице: GitHub ужимает каждую ячейку примерно до 430px,
и текст становится нечитаемым. Склей пару:

```bash
node $SKILL/scripts/pair.mjs --before raw/01-list-before.png --after raw/01-list-after.png \
  --out docs/pr/<slug>/01-list.png --diff --title "Список статей"
```

- Раскладку карточка выбирает сама: рядом, только если каждый кадр не шире 520 CSS px (мобильные,
  узкие крупные планы), иначе друг под другом во всю ширину.
- `--diff` сравнивает кадры попиксельно и обводит изменённые места: красным пунктиром на «Было»,
  зелёным на «Стало». Подходит для небольших правок (новая подпись, число, иконка), когда ручная
  метка лишняя. Снимай такие кадры **без** `--mark`, иначе разница меток тоже попадёт в обводку.
  Если отличается больше трети кадра (сдвиг вёрстки, другие данные), обводка не рисуется,
  а скрипт пишет предупреждение.
- Сырые кадры держи в scratch-папке, в `docs/pr/` клади только карточки: так в репозитории меньше
  файлов и веса.

### 4. Запиши GIF, если меняется взаимодействие

Один и тот же сценарий для обеих версий, до 15 секунд, видимый курсор:

```bash
node $SKILL/scripts/record.mjs --url http://localhost:5173/time --scenario flow.mjs \
  --clip "[data-testid=timesheet]" --out docs/pr/<slug>/02-add-entry-after.gif
```

В сценарии используй `click`, `type`, `mark`, `pause`, `scrollTo` (пример в шапке `record.mjs`).
Плавное движение курсора и паузы после ключевого шага нужны, чтобы зритель успел увидеть, что
произошло. Флаги подготовки (`--hide`, `--local-storage`, `--delay`, …) те же, что у `shoot.mjs`.

Качество:
- Кадры снимаются скриншотами в 2x, а не видео Playwright, и ужимаются до 1440px. Ширину не
  уменьшай без причины: GitHub сам вписывает картинку в колонку, и она остаётся чёткой.
- **`--clip <селектор>` почти всегда нужен.** Если сценарий идёт в одной панели или форме, обрежь
  запись по ней. Тогда изменение заполняет кадр, а не теряется точкой на экране 1440px, и файл
  меньше.
- Если GIF не влезает в 10 МБ, скрипт сам снижает fps, а потом ширину. Если и это не помогло,
  сократи сценарий или сузь `--clip`.
- `.mp4` вместо `.gif` (H.264) нужен для GitLab, где видео показывается прямо в описании, и для
  загрузки перетаскиванием в GitHub. Ссылку из репозитория GitHub показывает только как GIF.
- Записи с симулятора, эмулятора или экрана переводи через `--video` (`--start`, `--duration`,
  `--crop`, `--box`). Рецепт для iOS и Android лежит в `references/before-state.md`.

### 5. Диаграмма «было / стало» для технических задач

Mermaid не вставляется в PR как код: GitHub и GitLab рисуют его своей темой, цвета ломаются в тёмной
теме, а в письмах, превью Slack и мобильных приложениях вместо схемы виден текст. Диаграмму рендерит
`diagram.mjs` в PNG-карточку: панели «Было → Стало», легенда, счётчики и бейджи «новый / удалён /
изменён». Картинка лежит рядом со скриншотами и показывается везде одинаково.

1. Черновик по реальным импортам:
   ```bash
   node $SKILL/scripts/deps.mjs --base origin/main --head HEAD --lang ru > /tmp/deps.md
   node $SKILL/scripts/deps.mjs --base origin/main --level dir --importers --lang en > /tmp/deps.md   # крупнее, по папкам
   ```
2. Доведи черновик до истории: убери шум (утилиты, типы, неизменные связи), оставь 5–15 узлов,
   сгруппируй их в `subgraph` по слоям. Пример доводки лежит в `references/diagram-example.md`.
   Цель: ревьюер за 10 секунд видит, например, что «страница больше не ходит в API напрямую, а идёт
   через store». Цвета вручную не расставляй: `classDef`, `linkStyle` и `style` рендерер
   игнорирует.
3. Отрендери:
   ```bash
   node $SKILL/scripts/diagram.mjs --md /tmp/deps.md --out docs/pr/<slug>/05-deps.png \
     --title "Отчёты: данные через store" --lang ru --theme both
   ```
   Дифф рендерер считает сам: узел или связь (`a --> b`), которые есть только в «Было», он рисует
   красным пунктиром и зачёркивает, а те, что только в «Стало», выделяет зелёным. Если у узла с тем
   же id поменялись подпись или `subgraph`, он подсвечивается жёлтым. Поэтому **id узлов в обеих
   диаграммах должны совпадать**. Файл, у которого изменился код, но не связи, помечай вручную:
   `class api changed`. `--layout unified` рисует один общий граф с наложенным диффом (подходит для
   небольших правок), `--layout stack` ставит панели друг под другом. `--theme both` даёт
   `05-deps.png` и `05-deps-dark.png` для тега `<picture>`.
4. Если изменилась не структура импортов, а поток вызовов, напиши `sequenceDiagram` или `flowchart`
   «было / стало» руками (`--before a.mmd --after b.mmd`). Sequence рисуется в том же стиле, но без
   разметки диффа.
5. Открой PNG и посмотри на него глазами: подписи не обрезаны, бейджи не наезжают на связи, схема
   читается без подписи под ней.

### 6. Опубликуй медиа

Файлы лежат в `docs/pr/<slug>/` в ветке PR, где `<slug>` — короткое имя ветки или задачи. Называй их
`NN-сцена-before|after.png|gif`: номер держит порядок, суффикс сразу говорит, что это. Если в проекте
уже принято другое место (ветка `pr-assets/*` в памяти проекта или в прошлых PR), следуй ему.

Размер: PNG в 2x весит 300–600 КБ и навсегда остаётся в истории репозитория. Снимай крупные планы
через `--clip`, а не полные экраны 1440×900. Полный экран — только если важен контекст. `publish.mjs`
сам переводит PNG больше 200 КБ в палитру (обычно −60%), но только если картинка визуально не
изменилась (SSIM ≥ 0.995). Он предупреждает о PNG больше 800 КБ и о суммарном размере больше 8 МБ.

В описании PR (шаг 7) ссылайся на медиа **путями из репозитория**: `docs/pr/<slug>/01-x-after.png`.
Дальше всё делает один скрипт:

```bash
node $SKILL/scripts/publish.mjs --dir docs/pr/<slug> --body pr.md
```

Он коммитит только эту папку, пушит ветку (pre-push хуки проекта отрабатывают как обычно; если
хук падает из-за окружения, например у Playwright проекта не скачан браузер, почини окружение —
`npx playwright install chromium` — а не обходи хук) и проверяет, что коммит есть на remote и все упомянутые
файлы в нём лежат. Затем заменяет пути в `pr.md` на ссылки по SHA (GitHub: `blob/<sha>/…?raw=true`,
GitLab: `/-/raw/<sha>/…`) и обновляет PR или MR. Если `gh pr edit` падает из-за scope
`read:project`, он сам делает `gh api PATCH`. Добавил или переснял кадр — запусти ещё раз: старые
SHA-ссылки перепишутся на новый коммит. Если PR ещё нет, скрипт подскажет команду
`gh pr create --body-file pr.md` (её запускай после него). Хук отвергает коммит с одними картинками —
добавь `--no-verify`. В репозитории с двумя remote (GitHub и GitLab) укажи `--remote`.

В приватном репозитории картинки видят только участники, вошедшие в аккаунт. Проверка ссылки
через `curl` без токена даст 404 — это не ошибка, проверка идёт через git.

### 7. Собери описание PR

Шаблон и правила подписей лежат в `references/pr-template.md`. Весь текст пиши на языке из шага 0.
Под каждой сценой — строка «зачем» из шага 1. Создавай PR через `gh pr create --body-file` или
`glab mr create`, обновляй через `publish.mjs`. Не передавай описание через `--body "…"`: таблицы и
`<picture>` ломаются при экранировании.

### 8. Покажи результат пользователю

В финальном ответе о выполненной задаче приложи ссылку на PR и сами пары «Было / Стало». Если
интерфейс умеет показывать изображения по абсолютному пути (Markdown `![…](/abs/path.png)`), вставь их
прямо в ответ. Пользователь не должен открывать PR, чтобы увидеть результат.

## Перед отправкой проверь

- Язык PR выбран явно (по правилу проекта или после вопроса пользователю), и на нём написаны все
  заголовки, подписи к меткам и alt-текст.
- «Было» снято с актуальной базы того remote, куда идёт PR.
- У каждой сцены есть и «До», и «После» с одинаковыми параметрами, либо в PR написано, почему «До» нет.
- Скриншоты сцены собраны в карточку `pair.mjs`, а не стоят рядом в таблице; рамки охватывают
  текст, а не пустую ширину блока; плашки не закрывают контент; в кадре нет срезанных строк.
- Метки указывают именно на изменённое, подписи короткие и говорят, *что* изменилось.
- Под каждой сценой есть строка «зачем»: какое требование задачи она подтверждает.
- GIF есть для каждого изменения взаимодействия: обрезан по `--clip`, весит меньше 10 МБ, и в PR
  «Было» и «Стало» стоят друг под другом во всю ширину, а не в таблице.
- Для рефакторинга есть PNG-диаграмма «Было → Стало» из `diagram.mjs` (не сырой mermaid-блок) и скриншоты
  затронутых экранов без визуальных изменений.
- `publish.mjs` отработал без ошибок: ссылки ведут на SHA, файлы на месте, PR обновлён.
- На скриншотах нет секретов и реальных персональных данных.
- После `git worktree remove ../<repo>-pr-before` и остановки серверов не осталось висящих процессов.
